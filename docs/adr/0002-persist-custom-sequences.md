# Persist custom chord sequences in a local SQLite database

The app's chord sequences were not data: the six "famous" sequences lived as a hardcoded dict in `main.py` and searches depended on a `SEQ_FAMOSA` tag baked into `data/top/dataset_final.csv`. The feature now needs anonymous visitors to add sequences, all sequences (including the original six) to be searchable through the same flow, and the catalog to survive process and container restarts. Songs and genres must stay in the in-memory CSV path, and the app must stay a single local-only Docker container.

We introduced a SQLite database for the sequence catalog only, using Python's stdlib `sqlite3` and a single file at `/app/instance/sequences.db`. The schema has one `sequencias` table storing the ordered chord list, a unique canonical key, a nullable legacy key for the six originals, an origin marker, and a creation timestamp. On startup the app creates the table if needed and idempotently seeds the original six with fixed IDs 0–5 and their legacy keys; new sequences get IDs from 6 onward. Matching is computed in real time over the in-memory songs with one rule for every sequence: a contiguous, ordered slice of `musica.cifra` plus every song chord contained in the sequence's chord set. The legacy `?sequencia=` parameter is kept, and new `GET /sequencias`, `POST /sequencias`, and `?sequencia_id=` routes back the frontend catalog and creation flow.

SQLite was chosen because it is embedded, transactional, and already available in the Python 3.9 image, so it adds no service, no dependency, and no second container. The current gunicorn setup runs one worker by default, which is sufficient for this write volume. Persistence is completed at the Docker boundary: the image declares `/app/instance` as a volume, the documented run command uses a named volume, and `instance/` is excluded from the image and the repository. TinyDB, `shelve`/`dbm`/pickle/JSON files, DuckDB, and LMDB were rejected because they either add a dependency or trade away transaction and durability guarantees for little benefit; an in-memory database fails the restart requirement; and PostgreSQL/MySQL would introduce an external service that the single-container, local-only deployment explicitly avoids.

The cost is a new database lifecycle and an operational requirement: users who want the catalog to survive container recreation must mount the named volume, and startup must keep the seed idempotent. The open, anonymous catalog has no moderation or rate limiting, and the legacy `SEQ_FAMOSA` column remains in the CSV but is no longer the source of truth for sequence search. The matching rule is intentionally stricter than a loose chord-subset search, so new sequences may return fewer songs than users expect, and each search now scans the songs in memory. The deploy target is still undecided, as in ADR 0001; the decision here only adds local persistence and does not choose a cloud platform.

Scope is deliberately narrow: the catalog is append-only (no edit or delete), the 1–32 chord and 32-character limits are abuse protection rather than musical constraints, and the genre dropdown stays hardcoded for now. `SEQ_FAMOSA` remains in the CSV as the historical regression reference for the original six, not as a runtime dependency of the new sequence endpoint.
